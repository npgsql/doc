# 11.0 Release Notes

Npgsql.EntityFrameworkCore.PostgreSQL version 11.0 is currently in development. Previews are available on [nuget.org](https://www.nuget.org/packages/Npgsql.EntityFrameworkCore.PostgreSQL).

## Indexes over JSON members

EF 11 complex types mapped with `ToJson()` now support indexing JSON members through the existing `HasIndex` APIs, including unique and composite indexes. By default, these create B-tree expression indexes over the selected values; explicit GIN indexes can target `jsonb` arrays and subdocuments. See [Indexing JSON columns](../mapping/json.md#indexing-json-columns) for examples and limitations.

> [!NOTE]
> The provider currently references EF `11.0.0-rc.2.26504.105`, which has two temporary limitations: C# migration scaffolding for JSON member indexes fails because it cannot scaffold a `RelationalJsonIndex` literal, and composite member indexes with mixed ascending/descending directions fail before SQL generation. Uniform ascending or descending composites can generate SQL, but remain affected by the scaffolding limitation. Both issues are fixed in [dotnet/efcore#39089](https://github.com/dotnet/efcore/pull/39089); the provider has not yet consumed those fixes.

## PostgreSQL JSON functions with ToJson

The existing PostgreSQL JSON functions, such as `EF.Functions.JsonContains()` and `EF.Functions.JsonExists()`, can now be used with complex types and owned entities mapped with `ToJson()`, including nested objects and collections:

```csharp
var customers = await context.Customers
    .Where(c => EF.Functions.JsonContains(c.Details, """{"Name": "Joe"}"""))
    .ToListAsync();
```

## Support for PostgreSQL 18 temporal constraints

PostgreSQL 18 introduced powerful temporal constraints that allow enforcing data integrity over time periods directly at the database level. The EF Core provider now supports these features, allowing you to define temporal primary keys, unique constraints, and foreign keys.

### WITHOUT OVERLAPS for keys

Temporal primary and alternate keys use the `WITHOUT OVERLAPS` clause to ensure that for any given set of scalar column values, the associated time ranges do not overlap. This is useful for scenarios where you need to track historical data (e.g. employee records, pricing information, equipment assignments) while ensuring data integrity.

For example, an employee can have multiple records in the database (reflecting changes over time), but their validity periods must never overlap:

```csharp
public class Employee
{
    public int EmployeeId { get; set; }
    public string Name { get; set; }
    public string Department { get; set; }
    public decimal Salary { get; set; }
    public NpgsqlRange<DateTime> ValidPeriod { get; set; }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Employee>(b =>
    {
        b.Property(e => e.ValidPeriod)
            .HasDefaultValueSql("tstzrange(now(), 'infinity', '[)')");

        b.HasKey(e => new { e.EmployeeId, e.ValidPeriod })
            .WithoutOverlaps();
    });
}
```

This generates the following SQL:

```sql
CREATE TABLE employees (
    employee_id INTEGER,
    name VARCHAR(100) NOT NULL,
    department VARCHAR(50) NOT NULL,
    salary DECIMAL(10,2) NOT NULL,
    valid_period tstzrange NOT NULL DEFAULT tstzrange(now(), 'infinity', '[)'),
    PRIMARY KEY (employee_id, valid_period WITHOUT OVERLAPS)
);
```

### PERIOD for temporal foreign keys

Temporal foreign keys use the `PERIOD` clause to ensure that the referenced row exists during the entire time period of the referencing row. This maintains referential integrity across temporal relationships.

For example, when assigning employees to projects, the assignment period must fall within the employee's validity period:

```csharp
public class ProjectAssignment
{
    public int AssignmentId { get; set; }
    public int EmployeeId { get; set; }
    public string ProjectName { get; set; }
    public NpgsqlRange<DateTime> AssignmentPeriod { get; set; }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<ProjectAssignment>(b =>
    {
        b.HasOne<Employee>()
            .WithMany()
            .HasForeignKey(e => new { e.EmployeeId, e.AssignmentPeriod })
            .HasPrincipalKey(e => new { e.EmployeeId, e.ValidPeriod })
            .WithPeriod();
    });
}
```

This generates the following SQL:

```sql
ALTER TABLE project_assignments
ADD CONSTRAINT fk_emp_temporal
FOREIGN KEY (employee_id, PERIOD assignment_period)
REFERENCES employees (employee_id, PERIOD valid_period);
```

Temporal constraints also support NodaTime `Interval` and `DateInterval` properties when the NodaTime plugin is enabled. For more details, see the [temporal constraints documentation](../misc/temporal-constraints.md).

## Other new features

* [Generated `tsvector` columns and full-text expression indexes](../mapping/full-text-search.md#setting-up-and-querying-a-full-text-search-index-on-an-entity) now support integer and exact-numeric inputs by casting them to text ([#2615](https://github.com/npgsql/efcore.pg/issues/2615)).
* [`MapEnum`](../mapping/enum.md) now respects type-level `[PgName]` attributes when no PostgreSQL enum name is supplied ([#3379](https://github.com/npgsql/efcore.pg/issues/3379)).
* Added [`ModelBuilder.UseNoIdentityGeneration()`](../modeling/generated-properties.md#defining-the-default-strategy-for-the-entire-model) to disable the model's default PostgreSQL identity generation strategy ([#3723](https://github.com/npgsql/efcore.pg/issues/3723)).
* [Covering indexes](../modeling/indexes.md#covering-indexes-include) now support including properties nested within complex types mapped to regular columns.
* Indexes configured with [`IsCreatedConcurrently()`](../modeling/indexes.md#creating-indexes-concurrently) are now also dropped concurrently when removed by migrations ([#3901](https://github.com/npgsql/efcore.pg/issues/3901)).
* [Creating PostgreSQL extensions](../misc/other.md#postgresql-extensions) now uses `CASCADE` to install their dependencies automatically ([#3682](https://github.com/npgsql/efcore.pg/issues/3682)).
* Support specifying the encoding of newly created PostgreSQL databases with `ModelBuilder.UseDatabaseEncoding()` ([#3526](https://github.com/npgsql/efcore.pg/issues/3526)).
* Custom collation references now respect the model's default schema and correctly handle dots in collation and schema names across migrations, queries and scaffolding ([#4072](https://github.com/npgsql/efcore.pg/pull/4072)).
* `DateOnly.AddMonths()` and `DateOnly.AddYears()` now cast the result back to `date` (`CAST(dateOnly + INTERVAL '1 months' AS date)`), so that it can be projected, and are also translated for a `DateOnly` parameter. Previously, PostgreSQL returned a `timestamp`, which couldn't be read as a `DateOnly`.

See the [11.0.0 milestone](https://github.com/npgsql/efcore.pg/milestone/75?closed=1) for the full list of issues.

## Breaking changes

### PostgreSQL 16 is targeted by default

The provider now assumes at least PostgreSQL 16 by default, taking advantage of newer features (previously, PostgreSQL 14 was targeted). You can configure the targeted PostgreSQL version when configuring your context:

```c#
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    => optionsBuilder.UseNpgsql("<connection string>", o => o.SetPostgresVersion(14, 0));
```

### Changes to transient and concurrency exceptions

The default, non-retrying execution strategy no longer wraps transient failures in an additional `InvalidOperationException`. Applications catching that wrapper should instead handle the underlying exception.

In addition, PostgreSQL serialization failures (`40001`) and deadlocks (`40P01`) during `SaveChanges()` or `SaveChangesAsync()` now throw `DbUpdateConcurrencyException`, with the original `PostgresException` as the inner exception. This includes failures during an automatically committed transaction, but not a transaction committed explicitly by the application. Previously, these failures were generally exposed as `DbUpdateException` wrapped in `InvalidOperationException`.

These changes do not enable automatic retries. See [execution strategies](../misc/other.md#execution-strategy) and [database concurrency failures](../modeling/concurrency.md#database-concurrency-failures) for details ([#3098](https://github.com/npgsql/efcore.pg/issues/3098)).

### Date/time arithmetic on timestamptz is computed in UTC

Adding or subtracting a `TimeSpan` or `Duration` to a `DateTime`, `DateTimeOffset`, NodaTime `Instant` or `ZonedDateTime` mapped to `timestamp with time zone`, as well as `AddYears()`, `AddMonths()`, `AddDays()` etc. on `DateTime` and `DateTimeOffset`, is now computed in UTC, as `(x AT TIME ZONE 'UTC' + interval) AT TIME ZONE 'UTC'`. Previously, PostgreSQL added the interval's days and months in the session time zone, so that across a daylight saving time transition, `instant + Duration.FromDays(1)` added 23 or 25 hours rather than the 24 hours added by NodaTime and .NET. Such queries now return the same results as the equivalent .NET code, regardless of the session time zone. Values mapped to `timestamp without time zone` aren't affected. With the [legacy timestamp behavior](6.0.md#opting-out-of-the-new-timestamp-mapping-logic), arithmetic which follows the local time, like PostgreSQL's in the session time zone, isn't affected either: a `DateTime` mapped to `timestamp with time zone` is then a local date and time, whose arithmetic keeps the local time across a daylight saving time transition, and a `DateTimeOffset` has the local offset, in which `AddMonths()` and `AddYears()` add calendar months ([#4087](https://github.com/npgsql/efcore.pg/issues/4087)).

### TimeSpan and Duration components are truncated

`Days`, `Hours`, `Minutes`, `Seconds` and `Milliseconds` on `TimeSpan` and NodaTime `Duration` now return the same values as .NET for negative values, and for intervals computed in SQL (e.g. the difference between two timestamps). Previously, `Seconds` and `Milliseconds` were rounded down with `floor()`, whereas .NET truncates them towards zero (`TimeSpan.FromMilliseconds(-1500).Seconds` is -1, not -2). Each component was also read from a single one of PostgreSQL's interval fields, whereas an interval computed in SQL can have a time field of more than 24 hours, or with a different sign from its day field (e.g. `1 day -01:00:00`). The components are now computed from [`justify_hours()`](https://www.postgresql.org/docs/current/functions-datetime.html) ([#4088](https://github.com/npgsql/efcore.pg/issues/4088)).

### Negative TimeSpan and Duration values with days

PostgreSQL applies a sign in an interval [to the field it precedes only](https://www.postgresql.org/docs/current/datatype-datetime.html#DATATYPE-INTERVAL-INPUT), so `INTERVAL '-1 02:00:00'` is -1 day and +2 hours, i.e. -22 hours. Previous versions generated negative `TimeSpan` and `Duration` values with days that way, so that for example -26 hours became -22 hours in SQL literals (including seed data and default values in migrations). Negative values are now generated with a sign on both the days and the time (`'-1 -02:00:00'`), in SQL and in JSON. Seed data and default values already created by previous versions aren't changed ([#4086](https://github.com/npgsql/efcore.pg/issues/4086)).

Previous versions also wrote negative values with days in this format to JSON, meaning that the whole value is negative. By default, values with a sign on the days only (e.g. `"-1 02:00:00"`) are therefore still read from JSON with that meaning (-26 hours), so that JSON data written by previous versions is read back unchanged. If your JSON data was written by another application, which intended PostgreSQL's meaning (-22 hours), disable the `Npgsql.ParseOldEFCoreJsonTimeSpans` [AppContext switch](https://learn.microsoft.com/dotnet/api/system.appcontext) at the start of your application, before any Npgsql or EF Core operations are invoked:

```c#
AppContext.SetSwitch("Npgsql.ParseOldEFCoreJsonTimeSpans", false);
```

Like the other Npgsql AppContext switches, this applies to the whole application. It can also be set in your project file:

```xml
<ItemGroup>
  <RuntimeHostConfigurationOption Include="Npgsql.ParseOldEFCoreJsonTimeSpans" Value="false" />
</ItemGroup>
```

Values written by this version, values without days, and values read from `interval` columns aren't affected by the switch.

#### Migrating negative TimeSpan and Duration values in JSON

The `Npgsql.ParseOldEFCoreJsonTimeSpans` switch only applies when the provider reads JSON in .NET, e.g. when loading an entity or a whole JSON document. A query which evaluates a JSON member in PostgreSQL, e.g. filtering or ordering on it, or projecting the member alone, converts it to `interval` in PostgreSQL, which gives `"-1 02:00:00"` its PostgreSQL meaning (-22 hours). This was already the case in previous versions; in addition, since constants are now generated in the new format (`INTERVAL '-1 -02:00:00'`), comparing an old JSON value with a constant no longer matches. A query can't tell which format a value was written in, so existing JSON data with negative `TimeSpan` or `Duration` values with days must be converted to the new format manually, e.g. in a migration.

Convert each JSON property which holds a `TimeSpan` or `Duration`, by its path, rather than by searching the serialized JSON (which could also change unrelated strings). An old value has a sign on the days only (`-1 02:00:00`), and is converted by adding a sign to the time (`-1 -02:00:00`). For example, for a `Delay` property in a `jsonb` column `Details`:

```sql
UPDATE "Customers"
SET "Details" = jsonb_set(
    "Details",
    '{Delay}',
    to_jsonb(split_part("Details"->>'Delay', ' ', 1) || ' -' || split_part("Details"->>'Delay', ' ', 2)))
WHERE "Details"->>'Delay' LIKE '-% __:__:__%'
    AND "Details"->>'Delay' NOT LIKE '-% -%'
    AND "Details"->>'Delay' NOT LIKE '% % %';
```

For a nested property, use its full path in each place, e.g. `'{Address,Delay}'` in `jsonb_set()` and `"Details"#>>'{Address,Delay}'` instead of `"Details"->>'Delay'`. For a collection, convert each element of the JSON array, e.g. for a `Delays` property:

```sql
UPDATE "Customers"
SET "Details" = jsonb_set(
    "Details",
    '{Delays}',
    (SELECT jsonb_agg(
         CASE
             WHEN e #>> '{}' LIKE '-% __:__:__%' AND e #>> '{}' NOT LIKE '-% -%' AND e #>> '{}' NOT LIKE '% % %'
             THEN to_jsonb(split_part(e #>> '{}', ' ', 1) || ' -' || split_part(e #>> '{}', ' ', 2))
             ELSE e
         END
         ORDER BY i)
     FROM jsonb_array_elements("Details"->'Delays') WITH ORDINALITY AS a(e, i)))
WHERE jsonb_typeof("Details"->'Delays') = 'array' AND "Details"->'Delays' <> '[]';
```

For a collection of objects, convert the property of each element `e` in the same way, with `jsonb_set(e, '{Delay}', ...)`. These statements only change values in the old format; values without days, positive values, values already in the new format and `null` values are left unchanged, so they can safely be run more than once. Don't convert values written by another application which intended PostgreSQL's meaning (see the switch above).

> [!WARNING]
> Previous versions of the provider read the new format incorrectly: `"-1 -02:00:00"` (-26 hours) is read as -22 hours. Once 11.0 writes negative values with days to JSON, or the data is converted as above, it must no longer be read by applications using a previous version of the provider, e.g. during a rolling deployment where old and new versions run side by side, or after rolling back an upgrade. Upgrade all applications which read the JSON data before writing or converting it with 11.0.

### Initial migration rollback removes model-level objects

Rolling back a newly scaffolded initial migration now drops enum, range and collation definitions that were previously left behind. If other applications use these objects, the rollback can fail due to their dependencies; remove the corresponding drop operations from `Down()` if the objects must be preserved ([#3604](https://github.com/npgsql/efcore.pg/issues/3604)).

### Collation annotations containing literal double quotes

Previously scaffolded snapshots and migrations with raw collation annotation keys containing literal double quotes in collation or schema names can be misinterpreted by the new identifier encoding. They may fail to decode or reference the wrong collation; update affected annotation keys manually before using them with 11.0 ([#4072](https://github.com/npgsql/efcore.pg/pull/4072)).
