# Npgsql 11.0 Release Notes

Npgsql version 11.0 is in development.

> [!NOTE]
> We're considering to start dropping support for synchronous APIs (`NpgsqlConnection.Open`, `NpgsqlCommand.ExecuteNonQuery`, etc.) starting with Npgsql 11.0. The current plan is to deprecate the API by throwing a runtime exception by default (with a switch to re-enable synchronous I/O) for Npgsql 11.0, while possibly completely removing it for Npgsql 12.0. This is in line with ASP.NET Core and .NET APIs in general, which are moving in the direction of async I/O only (for example, `System.IO.Pipelines` doesn't have synchronous I/O). If you have any questions or want to share you experience/issues with async I/O, please feel free to post in the [issue](https://github.com/npgsql/npgsql/issues/5865).

## Breaking changes

### Removed multiplexing

Previous versions of Npgsql supported a high-performance mode called "multiplexing". While this mode could increase throughput in certain extremely-high-performance scenarios, it did not scale in highly-concurrent situations with many CPU cores, and added quite a bit of complexity to the codebase. We'll evaluate re-introducing a similar implementation that's more scalable and better-designed.

### Replication fixes that change behavior

Npgsql 11.0 fixes a number of bugs in the replication APIs. Some of these fixes change behavior that existing code may depend on:

* Npgsql now quotes slot and output plugin names, and escapes quotes in option names, option values and publication names, so all valid names work (e.g. slot names starting with a digit) and no name can change the replication command. Slot and plugin names are still folded to lower case, as before. If you escaped quotes in option values or publication names yourself, stop doing so.
* Ending a replication enumeration early (e.g. with `break` or because of an exception) now stops replication, so that the connection can be used again. Before, the connection stayed in replication mode and every other command failed. Physical replication stops by ending copy mode; logical replication stops by cancelling the replication command, which, like any error, drops the temporary replication slots of the session. Since the connection no longer replicates after that, `SendStatusUpdate()` now throws `InvalidOperationException` after the loop; send the status update before leaving the loop, or pass the position you processed as `walLocation` when you start replication again. On PostgreSQL 17 and earlier, a pgoutput stream that you start again on the same connection may lack the `RelationMessage`s, so use a new connection for it.
* Starting replication while another replication stream is active on the same connection now throws `NpgsqlOperationInProgressException`, without disturbing the active stream.
* A physical replication stream now ends normally when the server reaches the end of the timeline it streams (e.g. because the standby you stream from got promoted); before, the connection broke. Use `IdentifySystem()` and `TimelineHistory()` to continue on the new timeline. When the server ends a stream because it shuts down, Npgsql now throws `NpgsqlException`.
* In physical replication, the write position Npgsql reports to the server is now the end of the WAL it received. Before, it reported the server's WAL end, which made `synchronous_commit = remote_write` unsafe.
* `ReplicationConnection.CommandTimeout` now applies to replication commands and can be set before opening the connection. `Show("all")` now throws `NotSupportedException`.
* A `WalReceiverStatusInterval` or `WalReceiverTimeout` of zero now disables the corresponding timer, like in PostgreSQL, instead of flooding the server with status updates. Negative values other than `Timeout.InfiniteTimeSpan` now throw `ArgumentOutOfRangeException`.
* `SendStatusUpdate()` now throws when the status update couldn't be sent, instead of only logging the failure.
* Malformed pgoutput data (unknown message or tuple types, or changes for relations without a preceding `RelationMessage`) now breaks the connection with an exception, instead of leaving it in the middle of the stream. Column values can no longer be read after they were consumed (this throws `InvalidOperationException`), and `TupleEnumerator.Current` throws before the first `MoveNextAsync()`.

### Removed deprecated large object APIs

Npgsql 11.0 removes some APIs to support PostgreSQL [large objects](https://www.postgresql.org/docs/current/largeobjects.html); these were obsolete since Npgsql 8.0. The APIs were old and had some design issues, and were also not necessary, as the corresponding PostgreSQL functions can simply be called directly.
